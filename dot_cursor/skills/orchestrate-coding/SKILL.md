# Orchestrate: コーディング

## 適用基準

- 実装箇所が複数ファイルにまたがる
- 複数の専門領域（フロント/バック/インフラ等）が絡む
- 変更の影響範囲が広い

## 実装・レビューサイクル

```
├── Step 1: 計画
│   変更対象ファイルと方針を整理する
│
├── Step 2: 実装（サブエージェント群）
│   ファイルや領域ごとにサブエージェントを並列起動
│   各エージェントは担当範囲のみ変更する
│
├── Step 3: レビュー（サブエージェント）
│   実装結果を別エージェントがレビューする
│   観点: 正確性、一貫性、エッジケース、セキュリティ
│
└── Step 4: 修正
    レビュー指摘をもとに修正する
    重大な指摘があれば Step 2〜3 を繰り返す
```

### 計画（Step 1）

- 変更対象ファイルを列挙する
- ファイル間の依存関係を整理し、並列実行可能な単位に分割する
- 共有するインターフェース（型定義、API 契約等）を先に確定する

### 実装（Step 2）

サブエージェントへの指示:

```
以下のファイルを変更せよ。
- 対象: [ファイルパス]
- 変更内容: [具体的な指示]
- 守るべきインターフェース: [型定義や API 契約]
- 既存のコードスタイルに従うこと
```

並列実行時は、共有リソース（同一ファイルへの同時書き込み等）の競合を避ける。

### レビュー（Step 3）

レビューエージェントへの指示:

```
以下の変更をレビューせよ。
- 変更ファイル: [ファイルパス一覧]
- 変更の意図: [何を実現するための変更か]
- 観点: 正確性、一貫性、エッジケース、セキュリティ
- 問題があれば具体的な修正案を示すこと
```

### 修正（Step 4）

- レビュー指摘を分類する（必須修正 / 推奨 / 軽微）
- 必須修正がある場合は修正後に再レビュー（Step 2〜3 を繰り返す）
- 推奨・軽微はまとめて対応する

## 品質レビュー

- サブエージェントの成果物は必ずレビューしてからユーザーに返す
- 不十分な場合は具体的なフィードバックを添えて再委譲する
