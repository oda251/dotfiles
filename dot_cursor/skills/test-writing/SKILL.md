## エージェント構成

オーケストレーター（自分）が実装者を別エージェントとして立てる。
小規模タスク（単一ファイルの軽微な修正等）では自分で回してよい。

## スキップ条件

テストが不要なケース（設定ファイルの変更、既存テストが十分なリファクタリング、プロトタイプ等）はスキップし、直接 implementation に進んでよい。

## 手順

**実装者**が計画で定義した振る舞いをテストとして先に書く。この時点ではテストは失敗する（Red）。

正常系・異常系・境界値を網羅すること。

### テスト依存の境界

テストが本番と乖離しないことが最優先。mock は乖離の原因になるため最小限にする。

| 依存の種類 | 方針 |
|-----------|------|
| ステートフルな基盤（DB、キャッシュ、MQ等） | testcontainers で本物を立てる |
| 外部API・リモートサービス | HTTP レベルで mock（WireMock 等）。メソッドレベルの mock は避ける |
| ファイルシステム・環境変数 | テスト用の一時ディレクトリ / 変数で隔離 |
| 内部の純粋関数 | mock しない |

テスト対象自体を mock しない。テスト失敗時は実装を直す（テストが間違っている場合を除く）。

## 次のスキル

→ **test-review** を呼べ。テストファイルのパスを引き継ぐ。
