## 目的

実装タスクを 要件 → 赤テスト → 実装 → 緑 のループで進める。

責務を分ける：

- メイン（自分 / Opus）= 要件の明文化・観点議論・足場構築・赤緑の判定・simplify・push。赤テストは書いてよいが、プロダクションコードは書かない（実装は委譲する）。
- Sonnet サブエージェント（`Agent` tool, `model: sonnet`）= 実装。赤テストを委譲する場合のみ Sonnet-A に任せる。
- 不変条件: テスト作者 ≠ 実装者。赤テストを書いた者（メイン or Sonnet-A）と実装する Sonnet-B は別にし、実装者にはテストファイルを編集させない。実装者がテストを緩めて通すのを防ぐ。

---

## フロー

### Phase 0. テストを書くかの判断（要件ごと）

要件ごとに次の論理式で判断する。これは赤テストを書くかだけを決める判断で、ワークフロー全体（worktree・draft PR・実装・simplify・push）は常に実行する。

```
テストを書く = ( expect(fn(input)).toBe(output) が書ける ) && ( ビジネスロジック（ユースケース・バリデーション・変換等）に関わる )
```

- 真 → TDD ループ（赤 → 実装 → 緑）で進める
- 偽（UI 調整・設定変更・見た目など、振る舞いをアサートできない要件） → テストは書かず実装のみ行う

### Phase 1. 要件をテスト可能な粒度に明文化

タスクを検証可能なアサーションの箇条書きに分解する。1項目 = 赤テスト1つの粒度。

- 各項目は「入力 → 期待される振る舞い」または Given-When-Then で書く
- 「使いやすくする」のような検証不能な表現は禁止。`expect(fn(input)).toBe(output)` を書けるところまで具体化する
- 正常系・異常系・境界値を分けて並べる
- 関連ファイルを `Grep`/`Glob` で先に把握し、既存 IF と整合させる

### Phase 2. 不足観点をユーザと議論

`AskUserQuestion`（必要なら複数回、一度に詰め込まない）で確定していない観点だけを確認する：

- 異常系・境界値の扱い（エラー時の挙動、空入力、上限等）
- 非機能要件（性能・セキュリティ・後方互換）
- インターフェース設計の選択肢（命名・シグネチャ・公開範囲）

自明な点は聞かない。合意が取れたら要件リストを確定する。これが PR description と done 判定の基準になる。

### Phase 3. 足場（worktree + 空 draft PR）

確定要件をもとに足場を作る：

1. ブランチ名を決定（`feat/<slug>`, slug は英語 3〜6 語 kebab-case）
2. worktree を用意する。既に `feat/<slug>` の worktree 内にいれば再利用、なければ作成:

   ```bash
   gwq add -b feat/<slug>
   WT=$(gwq list -g --json | jq -r '.[] | select(.branch=="feat/<slug>") | .path' | head -1)
   ```

   以降、サブエージェントには `$WT` 絶対パスを毎回渡し、その中で作業させる。
3. 空コミット → push → draft PR 作成。PR body に確定要件をチェックリストで記載:

   ```bash
   git -C "$WT" commit --allow-empty -m "chore: scaffold <task>"
   git -C "$WT" push -u origin feat/<slug>
   gh pr create --draft --head feat/<slug> --title "<title>" --body "<要件チェックリスト>"
   ```

   PR body 例:
   ```markdown
   ## 要件
   - [ ] 正常系: <入力> → <期待>
   - [ ] 異常系: <入力> → <期待>
   - [ ] 境界: <入力> → <期待>
   ```
4. `TaskCreate` で各要件を1タスクとして登録し、進捗を可視化する。

### テスト基盤の確認（Phase 3 末 ＋ ループ中も随時）

赤テストを書く前に、そのテストを実行できる基盤があるか確認する。

- テストランナー / フレームワークが設定済みで、`expect(fn(input)).toBe(output)` を今すぐ走らせられるか
- そのテストに必要な fixture・シードデータ・テスト用 DB・モック基盤等が存在するか

基盤の整備自体が非自明な作業（シードデータ整備・テスト環境構築・新規ハーネス導入等）になる場合は、本ループで作り込まず別タスクに切り出す：

1. `AskUserQuestion` で「テスト基盤の整備が必要。別タスクに切り出すか？」を確認
2. yes なら `issue` で基盤整備タスクを起票し、本タスクはそれを前提条件に保留する（または基盤が要らない要件だけ先に進める）
3. 切り出した旨を PR description に追記

軽微なお膳立て（1〜2行の fixture 追加程度）はそのまま進めてよい。

### Phase 4–6. TDD ループ（要件1つずつ）

要件リストの先頭から1つ選び、以下を繰り返す。要件をまたいで同時着手しない。Phase 0 の判断でテストを書く要件は 4→5→6、書かない要件は 4・5 を飛ばして 6 のみ（実装後は振る舞いを直接確認し、全体テストの緑を担保する）。

#### 4. 赤テストを作る（メイン主体、委譲も可）

その要件について失敗するテストを1つ用意する。

- 既定: メインが直接書く
- 委譲する場合は `Agent`（`model: sonnet`）を Sonnet-A として起動する。サブエージェントは skill ファイルを自動ロードしないので、`${CLAUDE_SKILL_DIR}/red-test.md` を read して本文をプロンプトに埋め込み、＋ `$WT` ＋ テスト契約（IF・入力・期待出力・どのエッジか）＋ テストフレームワークを渡す

この時点では実装はしない。

#### 5. 赤を検証（メイン）

テストを自分で実行して検証する（委譲した場合もメインが再確認する）。

- テストが落ちているか（`git -C "$WT" ...` で test 実行）
- import error / typo ではなく、要件の振る舞いが未実装である理由で落ちているか
- アサーションが要件を表現しているか（`testing.md` 品質基準2: テスト対象を mock していない／振る舞いを検証している）

不適切なら自分で直す（委譲時は契約を直して Sonnet-A をやり直す）。

#### 6. 実装して緑にする（Sonnet-B）

赤テストを書いたのとは別の `Agent`（`model: sonnet`）を起動。`${CLAUDE_SKILL_DIR}/implement.md` を read して本文をプロンプトに埋め込み、＋ 以下:

- `$WT`
- 通すべきテストファイルのパス
- テストファイルは編集しない制約

実装後、メインが緑を検証する:

- 対象テストが緑
- 全体テストが緑（既存を壊していない）
- `git -C "$WT" diff -- <テストファイル>` が空（テスト未改変）

テストを書かない要件では「対象テストが緑」「テスト未改変」は適用外。振る舞いを直接確認し、全体テストの緑のみ担保する。

緑なら commit:
```bash
git -C "$WT" commit -am "feat: <要件>"
```
`TaskUpdate` で当該要件を completed にし、次の要件へ。

### Phase 7. 全要件 green → simplify

全要件が緑かつ PR チェックリストが埋まったら `/simplify` を実行する。その後、全体テストを再実行して緑を確認する。緑でなければ修正する。

### Phase 8. push

```bash
git -C "$WT" push
```

PR は draft のまま。完了をユーザに報告する（PR URL・満たした要件・残課題）。マージや draft 解除はユーザ判断に委ねる。

---

## ルール

- メインはプロダクションコードを書かない（実装は Sonnet-B に委譲）。赤テストは書いてよい。
- テスト作者 ≠ 実装者を常に守る。実装者 Sonnet-B はテストファイルを編集しない。
- 赤緑の判定（Phase 5・6 の検証）はメインが行う。サブエージェントの自己申告を鵜呑みにしない。
- テスト基盤の整備が非自明なら本ループで作り込まず別タスクに切り出す（「テスト基盤の確認」参照）。
- 言語/フレームワーク固有の作法は `~/.references/policy/{lang}.md`・`{lang}-{framework}.md`・`testing.md` に従う（委譲時はサブエージェントのプロンプトで指示）。
- 1ループ1要件。テストは1つずつ追加する。
