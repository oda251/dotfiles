# 仕様合意

実装方法を議論する前に、外から観察できる振る舞いを合意する。成果物はユーザーがレビューできる簡潔な概念プログラムであり、本番コードやテスト一式、想定可能なケースの網羅リストではない。

## 使う場面

- ユーザーから見える振る舞いが変わる機能・変更。
- 要件や例から複数の解釈が成り立つとき。
- ユーザーが仕様のモデル化・レビューを求めたとき。

振る舞いに影響しない変更（誤字修正など）では使わない。設計を検討する場合は、振る舞いモデルの承認後に [`design-alignment`](../design-alignment/SKILL.md) へ進む。

## 手順

1. **仕様の根拠を集める。** 利用可能な中で最も低コストの適切なサブエージェントに、読み取り専用で根拠調査を委譲する。ユーザーの依頼と調査対象の場所を渡し、次を報告させる。
   - 根拠となる正確なパス・節と、短い引用。
   - 明記された例、制約、権威ある資料同士の矛盾。
   - 依頼された振る舞いのうち、根拠が見つからないもの。

   調査エージェントは事実を集めるだけで、意図の決定、要件の創作、ファイル編集をしない。ユーザーの依頼と明示的な決定も根拠として扱う。新しい振る舞いの根拠として、実装詳細や既存テストを使わない。

2. **振る舞いの概念モデルを書く。** メインエージェントが短い自然言語の説明と図を作る。振る舞いに合う表現と作図ツールを選ぶ。
   - トポロジーが単純で自動レイアウトで十分なら、Mermaid、D2、PlantUML などのテキスト記述形式を使う。フロー、相互作用、状態遷移、構造化されたERモデルなどが対象。
   - 正確な配置、自由形式の注釈、複雑なデータモデルやコンポーネント図が必要なら draw.io などのビジュアルエディターを使う。編集可能なネイティブ形式を優先し、レビュー用に図データを埋め込んだ SVG を出力する。
   - Slidev / Marp は成果物自体がプレゼン資料の場合に限る。図のレイアウトツールではなく、Slidev で Mermaid を使っても Mermaid の図形・レイアウト上の制約は残る。

   入力、重要な判断や変換、観察可能な結果を示す。実装コンポーネント、クラス名、メソッド名はこのモデルに含めない。必要な振る舞い判断を説明できる最小の抽象度から始め、必要な箇所だけ詳細化する。

3. **エッジケースを絞る。** 根拠に明記された例外、振る舞いが変わる境界、契約上重要な失敗、ユーザーが明示したケースだけを短い表にする。条件、観察可能な結果、根拠または状態（`仕様に明記` / `ユーザー決定` / `未解決`）を記録する。推測を要件にしたり、細部で図を埋めたりしない。

4. **ユーザーとレビューする。** 振る舞いモデル、根拠、判断に必要な未解決点だけを提示し、解釈の確認・訂正を依頼する。振る舞いに影響する点が承認されるまで、設計、テスト作成、実装へ進まない。後の設計で振る舞いの不足が見つかったら、ここに戻って承認済みモデルを更新する。

5. **承認済みモデルを引き継ぐ。** 承認済みの振る舞いと根拠をレビュー成果物に記録してから [`design-alignment`](../design-alignment/SKILL.md) を呼び出す。テストは後で承認済み振る舞いモデルから作り、実装結果や内部設計図から作らない。

## レビュー成果物

GitHub では Issue 本文を簡潔に保ち、更新するモデルは Issue コメントに置き、PR本文からリンクする。中間モデルをPRのコード差分に含めない。

draw.io の場合は、図のプレビューになり、ダウンロード後に draw.io で再編集できるよう、図データを埋め込んだ SVG を添付する。GitHub CLI は SVG 画像を添付できる。SVG だけでは不十分な場合に限り、別の `.drawio` ファイルをブラウザーから添付する。GitHub がネイティブ描画できないテキスト形式では、レンダリングした SVG を添付する。

複雑な図は関心事ごとに分割し、短い説明や表を添える。大きな図を一枚に押し込んだり、混み合った図を解消するだけのためにスライド資料を作ったりしない。

## 関連

- 振る舞いの承認後は [`design-alignment`](../design-alignment/SKILL.md) で内部設計をモデル化する。
- dev/TDD の振る舞いテストは、この承認済みモデルだけを根拠にする。
