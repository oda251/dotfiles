# 仕様理解のすり合わせ

受け入れ条件やテストが、実装者の仕様解釈をそのまま写しただけになるのを防ぐ。テストや実装に着手する前に、根拠のある振る舞い解釈を作り、独立した読み手とユーザーの確認を得る。

## 使うとき

- 要件が曖昧、不完全、または資料同士で矛盾している
- 複数の妥当な振る舞いが考えられ、選択がテストや実装に影響する
- ユーザーが仕様の整理、受け入れ条件の作成、仕様解釈の確認を求めている

誤字修正など、振る舞いに影響しない変更には使わない。これは要件の正しさを自動保証するものではなく、ドメイン上の判断者はユーザーまたは指定された仕様の所有者である。

## 手順

1. **根拠を集める。** 元の依頼と、ユーザーが指定した仕様・資料・例を読み、参照箇所を記録する。コードや既存テストは新しい振る舞いの根拠にしない。互換性のために既存動作を維持する必要がある場合は、その制約をユーザーの要件として別に記録する。

2. **実装方法と分けて解釈案を書く。** 外から観測できる振る舞いを、具体例（入力 → 期待、または Given / When / Then）で表す。各項目に根拠を付け、明示された要件、ユーザーが決めた内容、未確定の仮定を区別する。曖昧さや矛盾があれば、可能な解釈を併記する。根拠のない仮定を確定要件にしない。

3. **ブラインドな独立レビューを行う。**
   - 解釈案を書いていない新規のエージェントに、まず元の依頼と根拠資料だけを渡す。解釈案、テストコード、実装はまだ見せず、期待される振る舞い・不明点・矛盾・境界例を独立に列挙してもらう。
   - その後、解釈案を見せて照合し、抜けや異なる妥当な読み方を洗い出す。
   - レビュー結果は仕様の根拠ではなく、ユーザーに確認する論点として扱う。レビュー担当者の多数決で仕様を決めない。
   - 独立した読み手を用意できない場合は、その制約を明示してユーザーに解釈案を確認してもらう。自分の読み直しを独立レビューとみなさない。

4. **ユーザーと合意する。** 振る舞いの要約、根拠、独立レビューで見つかった差分、未確定の選択肢を示し、解釈全体の確認を `AskUserQuestion` などで求める。曖昧さや矛盾が残る場合は、ユーザーまたは仕様の所有者が決めるまで受け入れ条件・テスト・実装に進まない。

5. **合意した振る舞いを受け入れ条件にする。** 各条件に、根拠となる仕様箇所またはユーザーの決定と、期待値がそこから導かれる理由を残す。実装を実行して得た値を期待値として転記しない。新たな曖昧さが見つかった場合は手順4に戻る。

## 成果物の形式

既存の要件ファイルがあればそこに記録し、なければタスクの成果物に適した場所へ記録する。

```markdown
## 根拠
- [資料と該当箇所]

## 合意した振る舞い
- [外から観測できる振る舞い]
  - 例: [入力] -> [期待]
  - 根拠: [資料の該当箇所、またはユーザーが明示した決定]

## 独立レビュー
- 一致した点: [...]
- 抜け・別の解釈: [...]

## 未決事項
- [質問、選択肢、根拠]

## ユーザー確認
- [合意した決定と会話上の根拠]
```
