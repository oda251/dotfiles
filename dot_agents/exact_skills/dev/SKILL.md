## 対象

このスキルは実装エージェント専用である。manager/administrator agent が `spec-alignment` と `design-alignment` を完了し、承認済み仕様と設計を引き継いだ後に使用する。仕様・設計の再作成、合意、図示、要件の追加質問は行わない。

実装対象はアプリコードだけでなく、設定ファイル、IaC、スキーマ、依存更新などリポジトリの変更全般に及ぶ。承認済みのGitHub Issue本文に記載された仕様を振る舞いの正本として扱う。

## 手順

1. **引継ぎを確認する。** Issue番号/URL、承認済み仕様本文、承認済み設計、対象リポジトリと作業ブランチを確認する。実装に必要な仕様・設計情報が欠けている、矛盾している、または理解不能な場合は推測で決定せず、managerへ停止して報告する。

2. **作業を分解する。** 承認済み仕様をテスト可能な振る舞い単位に分解し、承認済み設計に沿って実装順序を決める。複数要件を同時に着手しない。各項目を観察可能な入力と期待結果に対応付け、変更が意図せず仕様を拡張しないようにする。

3. **テストを先に確認する。** ビジネスロジックについて、入力と期待結果を表現できるテストが適切なら、変更前にテストを追加または実行し、振る舞い未実装で失敗することを確認する。既存テストの意図を確認し、テスト環境や基盤未整備で検証不能なら実装を進めず、具体的な不足をmanagerへ報告する。

   テストを編集する場合は振る舞いの回帰を防ぐ目的に限定し、テストだけを通すための仕様変更やモックでの設計固定をしない。

4. **最小実装を行う。** 承認済み設計の責務・境界・依存関係に沿い、現在の要件を満たす最小変更を行う。関連する既存パターン、リンター、型、フォーマット、依存管理を採用する。本タスクに不要なリファクタリングや仕様外の機能追加をしない。

5. **検証する。** 対象テスト、関連テスト、可能なら全体テストと静的検査を実行する。テストを書いた場合は対象テストが緑かつテストが意図した形で保持されていることを確認する。失敗は実装、環境、テストのいずれかを切り分け、根拠を残して修正する。

6. **仕上げる。** 差分をレビューし、承認済み設計と仕様に無関係な変更、生成物、秘密情報、不要なファイルを残さない。既存の手順に従ってコミットし、managerの指示に従ってPRまたはpushの処理を行う。

基盤未整備（シードデータ、テスト環境構築など）でテストや完了判定ができない場合は中断し、ユーザーではなくmanagerに進め方と必要な決定を報告する。
