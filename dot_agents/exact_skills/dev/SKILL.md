メイン（自分 / Opus）は要件設計・赤テスト・赤緑判定・push を担当し、実装は Sonnet サブエージェント（`Agent`, `model: sonnet`）に委譲する。実装する Sonnet にはテストを編集させない。

## 手順

1. `main` を基点に worktree を作り、要件ファイル `$WT/docs/tmp/<slug>.md` を用意する。本文では、適切なグラフタイプを選択し、求める振る舞いをmermaidで表現する。例外として、細かな例外処理など、プロジェクト固有でなく、葉がむやみに肥大するような表現はここでは避け、手順2のチェックリストで示す。

2. **テストや実装の前に、仕様理解をすり合わせる。**
   - 元の依頼と根拠となる仕様・資料を読み、実装方法とは分けて、外から観測できる振る舞いとして解釈を要件ファイルに書く。
   - 各振る舞いに根拠（依頼・仕様の箇所、またはユーザーが決めた内容）を付け、未確定・曖昧・矛盾する点と複数の解釈を明記する。根拠のない仮定を確定要件にしない。
   - 新規の独立したエージェントには、まず元の依頼と根拠資料だけを渡し、解釈案を見せずに期待される振る舞い・曖昧さ・矛盾を列挙してもらう。その後、要件ファイルの解釈案と照合し、抜けや別の妥当な読み方を挙げてもらう。テストコードや実装は見せない。レビュー結果は仕様の根拠ではなく、確認すべき論点として扱う。
   - 根拠と振る舞い例、未確定点をユーザーに示し、解釈全体の確認を `AskUserQuestion` で得る。曖昧さや不一致が残る場合は合意するまでテスト・実装に進まない。独立レビューを依頼できない場合も自己レビューで代替せず、その旨を示してユーザーに確認を求める。
3. 合意した振る舞いだけをテスト可能なアサーション（入力 → 期待）に分解し、根拠と期待値の理由を要件ファイルに記録する。1項目 = テスト1つの粒度。実装を実行して得た値を期待値に転記しない。
4. 異常系・境界・非機能・IF の不足観点を確認し、必要な追加判断は同じ仕様すり合わせを経て要件ファイルに反映する
5. 要件を1つずつ消化する（複数同時着手しない）。各要件で:

   1. テストを書くか判断する: `テストを書く = ( expect(fn(input)).toBe(output) が書ける ) && ( ビジネスロジックに関わる )`
   2. 書くなら、メインが赤テストを1つ書き、実行して振る舞い未実装で落ちることを確認する
   3. Sonnet のサブエージェントに `${CLAUDE_SKILL_DIR}/implement.md` と本タスクに関連する `~/.references` ポリシーのパス（選定基準は AGENT.md の `~/.references` マップ）を渡し、最小実装をさせる。サブエージェントはバックグラウンドで実行する。
   4. メインエージェントが検証する。テストを書いたなら対象テスト緑・テスト未改変、書かないなら振る舞いを直接確認
   5. commit する

6. 全要件 green になったら `/simplify` → 全体テスト緑を再確認する
7. push して draft PR を作成（PR body は要件ファイル）。一時ファイルは消す。draft のまま完了報告する

参考: [t-wada のTDDセッションログ](https://t-wada.hatenablog.jp/entry/red-green-tdd-with-claude-code-202610)（スキルではなく、コード前の論点整理と根拠に基づく判断例） / [mizchi の empirical-prompt-tuning](https://github.com/mizchi/skills/blob/main/empirical-prompt-tuning/SKILL.md)（独立した読み手、事前固定したチェックリストの考え方）

基盤未整備（シードデータ・テスト環境構築等）で赤テストが書けない要件は中断し、進め方をユーザと相談する。
