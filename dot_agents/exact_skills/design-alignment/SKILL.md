# 設計合意

承認済みの振る舞いをどう実現するか、内部構造が変更や品質をどう支えるかをモデル化する。設計モデルは振る舞い契約とは別の関心事であり、実装を形作るがテスト期待値を再定義しない。

## 使う場面

- [`spec-alignment`](../spec-alignment/SKILL.md) で振る舞いモデルが承認された後。
- 変更が複数コンポーネントに及ぶ、責務やデータ所有に影響する、既存機能との重複があり得る場合。
- ユーザーが実装前の内部設計レビューを求めた場合。

構造上の選択がない小さな変更では、アーキテクチャを無理に作らず設計メモを簡潔にする。

## 手順

1. **承認済みの振る舞いモデルを読む。** 成果物のリンクと版を記録する。モデルがない、または承認されていない場合は停止し、先に `spec-alignment` を使う。

2. **既存部品を調査する。** 利用可能な中で最も低コストの適切なサブエージェントに、対象を絞った読み取り専用のリポジトリ調査を委譲する。承認済みモデルに必要な機能だけを調べ、関連候補ごとに次を報告させる。
   - ファイルパスとシンボル、責務、公開入出力、既知の制約。
   - 現在の役割が分かる呼び出し元・利用箇所・テスト。
   - そのまま適合するか、改修で解消できる不足は何か、新規作成が必要になり得る理由。
   - 変更する場合に影響しそうな範囲と再確認すべきテスト。

   調査結果は実装上の事実であり、望ましい振る舞いの根拠ではない。観察した事実と提案を分け、コードを編集しない。

3. **設計の概念モデルを作る。** メインエージェントが責務、境界、依存関係、関係するデータ所有を自然言語と図で表す。コンポーネント・依存関係図、概念データモデル、コンポーネント間の相互作用など、目的に合う最小の図を選ぶ。部品を `既存` / `改修` / `新規` と示し、候補部品の再利用・拡張より新規作成がよい場合は理由を書く。

   すべての図はD2で表現する。フロー、相互作用、データモデル、コンポーネント構造など、レビューに必要な視点をD2の図として示す。

   責務、再利用、品質上のトレードオフを判断できる範囲に留める。実際のインターフェースや設計判断に影響しないクラス・メソッド構造を推測しない。一般的な網羅チェックリストではなく、結合度、責務の重複、変更容易性、テスト容易性など重要な懸念を示す。

4. **ユーザーと設計をレビューする。** `mise exec -- d2 --watch --browser=0 <model.d2>` でD2 devserverを起動してURLをユーザーに示す。WSLでは `openurl <URL>` でホストWindowsの既定ブラウザーに表示し、設計モデル、代替案、根拠、トレードオフを提示する。対話中の訂正をD2ソースへ反映し、実装前に承認を得る。設計上の選択を新しいプロダクト要件として扱わず、レビュー後はdevserverを停止する。

5. **仕様が必要なら戻る。** 設計で外から見える振る舞いの不足や矛盾が見つかったら、設計内で決めない。`spec-alignment` に戻り、新たな振る舞いの承認版を記録してから、影響する設計判断を見直す。

6. **テストと実装へ別々に引き継ぐ。** 振る舞いテストは承認済みモデルだけから作る。内部構造を固定するテストや、設計を強制するためだけに内部呼び出しをモックするテストは作らない。構造上の制約は、適切なコードレビュー、静的検査、既存のアーキテクチャ検査で扱う。

## レビュー成果物

合意した設計図はPR本文にSVGとして掲載し、D2ソースは折りたたみ可能な `<details>` 節に含める。`gh pr edit --body-file <body.md> --attach <design.svg>` で画像を添付できる。設計図ファイルをPRのコード差分に含めない。設計で仕様の修正が必要になった場合は、先に仕様をIssueコメントで更新してから設計図を確定する。

GitHub はD2をネイティブ描画しないため、対話中はdevserverで図を見せ、合意後はPR本文のSVGで図を直接見られるようにする。SVGは `mise exec -- d2 <input.d2> <output.svg>` で生成する。

複雑な設計は関心事ごとの図に分割し、簡潔な表を添える。

## 関連
