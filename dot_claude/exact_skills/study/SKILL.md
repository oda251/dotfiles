学習を Q&A セッションとして進め、同時に vault に学習ノートとして蓄積する。最後にユーザの合図で記述式クイズを実施し理解を確認する。

## 適用範囲

このスキルは **題材が普遍的に通用する学習** に限定する。判断基準は「同じ説明が **別のプロジェクトの読者にもそのまま価値を持つか**」。

| トリガーする | しない |
|---|---|
| 「Reactのレンダリングの仕組みを教えて」 | 「このSvelteKitプロジェクトのrendering modeどう設定してる？」 |
| 「JWTってどう動くの？」 | 「この repo のauth middlewareの流れ追って」 |
| 「CAP定理って？」 | 「我々のDB構成のトレードオフを整理して」 |

ハイブリッド（一般概念 + 自プロジェクト実例）の場合は **一般部分のみ** をノート化し、プロジェクト固有の話は会話に留める。それでも残したいなら docs スキルへ。

## フェーズ構成

```
[1] 初回質問への回答 + ノート作成
        ↓
[2] 追加質問ループ（性質に応じて QA 追記 / 本文更新 / 両方）
        ↓ ユーザの「クイズ」「テスト」等の合図
[3] 記述式クイズによる理解確認
```

ユーザが単語に明示言及した場合は [1]/[2] と並行して **単語ページ (term/)** を作成する。詳細は `references/term-pages.md`。

## 共通ルール

- vault 操作は `obsidian` コマンド経由のみ。ファイルシステム直書き禁止
- 出典・未検証マーカーの扱いは `~/.references/policy/documentation.md` に従う
- 確認できない事項は捏造せず「わかりません」と明言
- 本文は学習者目線で書く。専門用語は初出時に簡潔な定義を添える

## [1] 初回回答 + ノート作成

1. ユーザの質問にまず会話で答える（簡潔に。詳細はノートで）
2. ノートを作成する

### ノートパス

```
note/{date}-{topic-slug}.md            # 通常はこちら
{org}/note/{date}-{topic-slug}.md      # 明確に特定リポジトリの学習なら
term/{word-slug}.md                    # 単語への明示言及時（references/term-pages.md 参照）
```

- `date` = `YYYY-MM-DD`
- `topic-slug` = kebab-case。題材がわかる粒度（例: `tcp-congestion-control`, `react-useeffect-deps`）
- `{org}` = `git remote get-url origin` から抽出。原則 repo-less でよい

### ノート構造

```markdown
---
tags:
  - purpose/study
  - topic/<topic>
  - tech/<tech>   # 該当時
---

# {タイトル}

> 学習開始: {date}

## 概要

{1〜3段落で要点。インライン出典付き}

## 詳細

{セクション分け。コード例・図（mermaid）も活用}

## 参考

- [{タイトル}]({URL})
```

`## QA` のような QA 用ラッパーセクションは **置かない**。追加質問は `### Q: ...` エントリとして末尾に直接 append する（後述）。

### 作成コマンド例

```bash
cat > /tmp/study.md << 'EOF'
---
tags:
  - purpose/study
  - topic/networking
  - tech/tcp
---

# TCP 輻輳制御

...
EOF
obsidian create vault=obsidian-vault path="note/2026-05-11-tcp-congestion-control.md" content="$(cat /tmp/study.md)"
```

作成後、`obsidian open vault=obsidian-vault path="..."` で開けることをユーザに伝える。

## [2] 追加質問ループ

追加質問が来たら **性質を分類** してから反映する:

| 質問の性質 | 例 | 反映先 |
|---|---|---|
| (A) 概念に関する新規質問 | 「Slow Start と Congestion Avoidance の違いは？」 | 末尾に `### Q: ...` で追記 |
| (B) 本文の記述に対する質問/疑問 | 「『閾値』って具体的に何の値？」「ここの説明があいまい」 | 本文の該当箇所を更新（明確化・補強・訂正） |
| (C) 両方の性質を持つ | 概念質問だが、答えると本文の弱い部分が露呈する | (A) と (B) の **両方** を行う |
| (D) 本文に要改善事項が発覚 | 回答中に本文の誤り・抜け漏れに気付いた | 本文を更新（QA追記は質問次第） |

### 判断手順

1. 質問を読み「ノート本文の特定箇所への言及があるか」を確認
   - あり → (B) または (C)
   - なし → (A) だが、回答を組み立てる過程で本文の弱点が見つかれば (C)/(D) に昇格
2. 回答を会話で返す
3. 上記表に従い vault を更新

### QA 追記 (A/C)

`obsidian append` で末尾に `### Q: {質問要約}` 見出しと回答本文（インライン出典付き）を追記する。フォーマット・コマンド形は [1] の作成例に準じる。

### 本文更新 (B/C/D)

`obsidian read` で現在の本文を確認 → 該当箇所を特定 → `obsidian replace` または書き直しで更新。

- 単純な差し替えは `obsidian replace` を使う
- 大きな書き換えは該当セクションを `obsidian read` → 編集 → 該当セクションを置換
- 変更の意図（何を明確化したか）は **コミットメッセージのように本文構造で表現** する。本文中に「追記:」「訂正:」などのメタ注釈は残さない（ノートは最終状態であるべき）

## [3] クイズフェーズ

### 起動条件

**ユーザの明示的合図のみ** で起動する。Claude から自発的に「クイズしますか？」と促してはいけない。

合図の例: 「クイズ」「クイズして」「テスト」「確認テスト」「理解度チェック」「quiz」「test」

### 進め方

1. 起動時にユーザに以下を確認:
   - 出題数（デフォルト: 3問）
   - 出題範囲（デフォルト: ノート全体）
   - 難易度（デフォルト: 中。「基礎中心」「応用含む」など）
2. **記述式（自由回答）** で1問ずつ出題。一度に複数問出さない
3. ユーザの回答に対し:
   - 模範解答と照合し、合致点・不足点・誤りを具体的に指摘
   - 出典をインラインで添えて補足
   - **誤答や答えられなかった項目はノートの該当箇所が弱い可能性が高い**。本文を読み直し、必要なら更新する（フェーズ2の (D) と同じ扱い）
4. 全問終了後、総評を出す:
   - 強い領域 / 弱い領域
   - 復習推奨セクション
   - ノートに改善を加えた場合はその要約

### 出題の質

- 単純な暗記より「なぜそうなるか」「いつ使うか」「他の概念との違い」を問う
- ノートに書いてある事実をそのまま聞くのではなく、ノートを理解していないと答えられない問いにする
- ただし範囲はノート本文の内容に限定する（範囲外を出して詰めるのは目的に反する）

## セルフチェック

完了前に確認:

- 追加質問の性質分類（A/B/C/D）に従って QA 追記 / 本文更新を正しく行ったか
- クイズはユーザの明示合図を待ったか（自発的に促していないか）
- クイズで露呈した弱点をノートに反映したか
- term ページを扱った場合は `references/term-pages.md` のセルフチェックも確認したか
