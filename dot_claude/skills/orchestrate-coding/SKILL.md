## 実装・レビューサイクル

サイクルはタスクの規模によらず同じ。小規模ならサブエージェントを使わず自分で回す。

```
├── Step 0: 調査
│   技術選定や仕様確認が必要なら orchestrate-research で調査する
│
├── Step 1: 計画
│   変更対象ファイルと方針を整理する
│
├── Step 2: 実装
│   ファイルや領域ごとに並列実装する
│
├── Step 3: レビュー
│   実装結果を実装者とは別の視点でレビューする
│   観点: 正確性、一貫性、エッジケース、セキュリティ
│
├── Step 4: 修正
│   レビュー指摘をもとに修正する
│   重大な指摘があれば Step 2〜3 を繰り返す
│
└── Step 5: 検証
    テスト実行・ビルド確認で変更の正しさを検証する
```

### 調査（Step 0）

orchestrate-research スキルに従ってリソースにアクセスし、必要な情報を収集する。

- **要件の調査**: 何を作るか不明確な場合、ユーザーの意図や対象ドメインの仕様を調べる
- **設計の調査**: どう作るかについて、ベストプラクティス・既存コードのパターン・ライブラリの推奨用法を調べる

新規実装や設計判断を伴う変更では、設計の調査を必ず行う。
既存コードの軽微な修正（バグ修正、リネーム等）のみスキップしてよい。

### 計画（Step 1）

- 変更対象ファイルを列挙する
- ファイル間の依存関係を整理し、並列実行可能な単位に分割する
- 共有するインターフェース（型定義、API 契約等）を先に確定する
- 要件が不明確、または判断が分かれる設計上の選択肢がある場合は、実装に進まずユーザーに確認する。推測で実装しない

### 実装（Step 2）

サブエージェントへの指示:

```
以下のファイルを変更せよ。
- 対象: [ファイルパス]
- 変更内容: [具体的な指示]
- 守るべきインターフェース: [型定義や API 契約]
- 既存のコードスタイルに従うこと
```

並列実行時は、共有リソース（同一ファイルへの同時書き込み等）の競合を避ける。

### レビュー（Step 3）

レビューエージェントへの指示:

```
以下の変更をレビューせよ。
- 変更ファイル: [ファイルパス一覧]
- 変更の意図: [何を実現するための変更か]
- 観点: 正確性、一貫性、エッジケース、セキュリティ
- 問題があれば具体的な修正案を示すこと
```

### 修正（Step 4）

- レビュー指摘を分類する（必須修正 / 推奨 / 軽微）
- 必須修正がある場合は修正後に再レビュー（Step 2〜3 を繰り返す）
- 推奨・軽微はまとめて対応する
- 原因不明のエラーが発生した場合は core-protocols のデバッグプロトコルを適用する

### 検証（Step 5）

- テスト実行（既存テストの pass 確認、必要なら新規テスト追加）
- ビルド確認
- 検証が失敗した場合は Step 4 に戻る
