# SSR/SSG/ISR ユースケース別選定基準 — 収集ファクト

## Source 1: SvelteKit 公式ドキュメント — Page options

URL: https://svelte.dev/docs/kit/page-options

- プリレンダリング（SSG）の適用条件: "For a page to be prerenderable, any two users hitting it directly must get the same content from the server." — すなわち、全ユーザーに同一コンテンツを返すページのみ SSG 可能
- プリレンダリング不可のケース: パーソナライズされたコンテンツを含むページ、form actions を使うルート（POST リクエスト処理が必要）、`url.searchParams` を使用するページ
- `prerender = 'auto'` を使うと、プリレンダリングしつつ動的 SSR マニフェストにも含められる。人気コンテンツを静的配信しつつフォールバックも維持する用途
- SSR を無効化（`ssr = false`）するユースケース: `document` などブラウザ専用 API を使う場合のみ
- CSR を無効化（`csr = false`）すると JS ハイドレーションなし。HTML/CSS のみで動作するページ向け。フォームのプログレッシブエンハンスメント不可、リンクはフルページナビゲーション
- 戦略の混在が可能: マーケティングページはプリレンダリング、動的ページは SSR、管理画面は CSR のみ、というハイブリッド構成を同一アプリ内で実現できる
- 子ルートが親レイアウトの設定を上書きできるため、アプリ全体をプリレンダリングにしつつ特定ページだけ動的レンダリングにすることが可能

## Source 2: SvelteKit 公式ドキュメント — Project types

URL: https://svelte.dev/docs/kit/project-types

- デフォルト（ハイブリッド）レンダリング: 初回ロードは SSR、以降のナビゲーションは CSR。SEO とパフォーマンスの両立が目的
- adapter-static を使えば完全な SSG サイトとして構築可能。コンテンツ中心のサイトに適する
- 大規模な静的サイトでビルド時間が問題になる場合、adapter-vercel の ISR（Incremental Static Regeneration）でビルド時間を回避できる
- SPA（CSR のみ）: 別バックエンドがある場合やバックエンド不要な場合に有効。ただし SSR と比較して SEO・パフォーマンスが劣る
- MPA（csr = false）: SvelteKit は従来型 MPA 向けには設計されていないが、特定ページで JS を無効化することは可能
- アダプター選択がデプロイ方式を決定し、コードベースの構造変更なしに後から切り替え可能

## Source 3: Vercel Blog — How to choose the best rendering strategy for your app

URL: https://vercel.com/blog/how-to-choose-the-best-rendering-strategy-for-your-app

- 選定の5つの判断軸:
  1. コンテンツ更新頻度: 静的コンテンツ→SSG、定期更新→ISR、リアルタイムデータ→SSR/CSR
  2. SEO 要件: 検索可視性が重要なページは静的またはサーバーレンダリングを優先（Core Web Vitals がランキングに影響）
  3. ユーザーインタラクションレベル: 少ない→SSG/ISR＋軽量JS、多い→SSR＋クライアントハイドレーションまたはCSR
  4. 読み込み速度要件: 最速→SSG or 低頻度 ISR、鮮度とスピードのバランス→ISR or SSR
  5. パーソナライズ: パーソナライズが必要→SSR or CSR。SSG ではパーソナライズ不可。ISR はキャッシュされたパーソナライズには対応可能な場合あり
- 戦略別の推奨ユースケース:
  - SSG: サイトレイアウト、パフォーマンス重視のマーケティングページ、ドキュメント
  - ISR: EC 商品ページ、ニュースサイト、大規模コンテンツサイト（フルリビルドが非現実的な規模）
  - SSR: パーソナライズされたダッシュボード、SNS フィード、リアルタイムデータ可視化
  - CSR: 即時フィードバックが必要なユーザー操作、外部データとのリアルタイムインタラクション
- パフォーマンス比較:
  - TTFB: SSG=最速, ISR=最速, SSR=最遅, CSR=中間
  - サーバーリソース: SSG=最低, ISR=低, SSR=高, CSR=最低
  - データ鮮度: SSG=静的, ISR=定期的, SSR=リアルタイム, CSR=リアルタイム
- 「最も効果的なアプリケーションは、単一戦略に依存するのではなく、異なるコンポーネントごとに最適なレンダリング方式を組み合わせる」

## Source 4: robino.dev — When and Where to Render

URL: https://blog.robino.dev/posts/rendering-strategies

- ビルド時レンダリング（SSG）のユースケース: 静的コンテンツ、CMS から取得して一度キャッシュできるコンテンツ。「リクエストごとではなくビルド時に一度だけタスクを実行できる」ことが利点
- SSG の制約: 頻繁に更新されるコンテンツやユーザー固有のコンテンツには不適。データ更新にはリビルドが必要
- SSR のユースケース: リクエストごとに新鮮なデータが必要な動的コンテンツ、SEO 重要ページ
- SSR のトレードオフ: リクエストごとのレンダリングでレスポンス時間増加、HTML ペイロード増大、ハイドレーションコスト（「同じ JavaScript をサーバーとクライアントで二重実行する」）
- CSR のユースケース: 頻繁な更新が必要な高インタラクティブアプリケーション、リアルタイム動的レンダリング
- CSR の制約: プリレンダリング HTML 送信より一般的に遅い、検索エンジンクローラーが JS レンダリングコンテンツを確実に読めない可能性、レイアウトシフトやローディングスピナーの発生
- ISR のユースケース: フルリビルドなしで定期更新が必要な動的コンテンツ。パフォーマンスと鮮度の両立
- 判断指針: 「公開向けコンテンツにはパフォーマンス優先（ビルド時/ISR）、パーソナライズ体験にはサーバーレンダリング、インタラクティビティには CSR を選択的に使用」

## Source 5: This Dot Labs — A Deep Dive into SvelteKit's Rendering Techniques

URL: https://www.thisdot.co/blog/a-deep-dive-into-sveltekits-rendering-techniques

- SvelteKit のプリレンダリング: 「ビルド時にウェブページのスナップショットを撮り、追加処理なしで配信する」。読み込み最速、サーバー負荷最小、SEO 優秀
- プリレンダリングの最適ユースケース: 静的コンテンツ（ブログ、ドキュメント、ランディングページ）、パーソナライズ不要のページ、SEO 重視コンテンツ、ユーザー間で変化しないコンテンツ
- プリレンダリングの制約: ページ数が多いとビルド時間が延びる、動的・ユーザー固有コンテンツには不適、ビルドフェーズでのデータ取得が必要
- SSR の最適ユースケース: 動的・ユーザー固有コンテンツが必要なアプリ、リアルタイム更新・パーソナライズ体験、EC プラットフォーム・ユーザーダッシュボード、動的コンテンツを持つ SEO 依存アプリ
- SSR の制約: 高トラフィック時にサーバーリソース集約的、リクエストごとの計算オーバーヘッド、高インタラクティブ・リアルタイムアプリには最適でない、リソース制約下でパフォーマンスボトルネックの可能性
- CSR の最適ユースケース: 高インタラクティブアプリ、SPA、頻繁なリアルタイムコンテンツ更新、管理パネル・複雑な UI
- CSR 無効化の判断: インタラクティビティ不要のページ（静的 about ページ、ドキュメント）では `csr = false` で JS バンドルサイズ削減・初期ロードパフォーマンス向上
- 具体的な選定マトリクス:
  - 静的ブログ/ドキュメント → プリレンダリング（高速ロード、パーソナライズ不要）
  - パーソナライズ付き EC → SSR（動的コンテンツ＋SEO 重要）
  - 管理ダッシュボード → CSR（SSR 無効）（リアルタイムインタラクティビティ優先）
  - マーケティングランディングページ → プリレンダリング（パフォーマンス重視、コンテンツ安定）
  - ニュースフィード/リアルタイムデータ → SSR（動的＋パーソナライズ＋SEO）
  - ログイン後の内部ツール → CSR（SEO 不要、インタラクティビティ必須）

## Source 6: PkgPulse Blog — SSR vs SSG vs ISR vs PPR: Rendering 2026

URL: https://www.pkgpulse.com/blog/ssr-vs-ssg-vs-isr-vs-ppr-rendering-2026

- 選定フローチャート:
  - 全ユーザーに同一コンテンツ＋更新頻度低い → SSG
  - 全ユーザーに同一コンテンツ＋定期更新 → ISR
  - 静的/動的セクション混在 → PPR
  - 完全にユーザー固有の動的コンテンツ → SSR
- SSG の具体的ユースケース: ドキュメントサイト（「コンテンツはプッシュ時に変わる、ユーザーごとではない」）、マーケティングランディングページ、ブログ記事・編集コンテンツ、ポートフォリオサイト
- SSG の制約: 更新にはフルリビルドが必要で、大規模サイトや頻繁な変更には非現実的
- ISR の具体的ユースケース: EC 商品カタログ（価格・在庫の定期更新）、ニュースサイト（毎時の記事更新）、イベントリスト、CMS ベースのドキュメント（コンテンツチームが定期公開）
- ISR の利点: ユーザーは再生成を待つ必要がない（キャッシュ版を配信しつつバックグラウンドで更新）。Webhook による即時無効化もサポート
- ISR の制約: 個別ユーザーごとのパーソナライズは不可
- SSR の具体的ユースケース: 認証付きダッシュボード（ユーザー固有コンテンツ）、リアルタイムデータ（ライブスコア、在庫、秒単位で変わる価格）、チェックアウトフロー（正確なカート状態が必要）、検索結果ページ（クエリパラメータ駆動）、サーバーサイド A/B テスト
- SSR のトレードオフ: TTFB が高い（200-500ms）、サーバー負荷大、フルページ CDN キャッシュ不可
- TTFB 比較: SSG/ISR = 20-50ms（CDN 配信）、SSR（ウォーム）= 80-200ms、SSR（コールドスタート）= 300-900ms
- SvelteKit のフレームワーク対応状況: SSG=対応、ISR=アダプター依存（adapter-vercel 等）、SSR=デフォルト対応、PPR=未対応

## Source 7: DEV Community — Rich Harris explains why SvelteKit pushes for SSR

URL: https://dev.to/mandrasch/rich-harris-explains-why-sveltekit-pushes-for-server-side-rendering-and-against-spa-5flj

- Rich Harris の SSR 推奨理由: Google ボットは JS を実行するが「純粋な HTML スキャンと比較して信頼性が低く、頻度も少ない」。SSR コンテンツのほうが確実かつ頻繁にインデックスされる
- SSR はデータ取得を即座に行える。CSR ではページロード後にデータ取得が発生するため遅延が生じる
- SSR のレジリエンス: クライアントサイド JS は開発者の制御を超えた要因で予期せず失敗する可能性があるが、サーバーサイド実行はより安定
- Harris の基本方針: 「非常に正当な理由がない限り SPA を使うな」
- CSR が適切なケース（記事内の反論として）: ネイティブソフトウェアに近いアプリ（Figma, Spotify, Google Drive）。インタラクティビティが複雑さを正当化する場合
- SSG は CDN 配信でサーバーインフラ不要という中間策だが、1,000 ページ超の大規模コンテンツライブラリでは課題あり

## Source 8: Crystallize Blog — Web Rendering Explained

URL: https://crystallize.com/blog/web-rendering

- SSR のユースケース: EC サイト、SEO が必要なコンテンツ重視サイト、パーソナライズされた動的コンテンツページ、認証済みユーザー体験。パフォーマンス特性は「高速な初回描画、サーバーコスト高」
- SSG のユースケース: ブログ・マーケティングサイト、ドキュメント、パンフレットサイト、更新頻度の低い商品リスト。パフォーマンス特性は「非常に高速、ランタイムコスト最小」
- ISR のユースケース: 大規模 EC カタログ、コンテンツ重視のコマースサイト、在庫やニュース更新のあるプラットフォーム。パフォーマンス特性は「静的に近い速度で鮮度も確保」
- ISR のトレードオフ: キャッシュリフレッシュサイクル中にユーザーが古いコンテンツを受け取る可能性。時間に敏感なデータでは信頼性に影響
- CSR のユースケース: SPA、ダッシュボード・内部ツール、SEO 不要のアプリ、高インタラクティブなバックオフィスシステム。初期ロードは遅いがその後のインタラクションは高速
- SEO 観点: 「SSR は SEO において優れている」。Google が JS を解析できるにもかかわらず、CSR はコンテンツ重視サイトには不適
- 判断フレームワーク: 「パフォーマンス、SEO 要件、インタラクティビティ、コンテンツの動的性」の4要素で選択
