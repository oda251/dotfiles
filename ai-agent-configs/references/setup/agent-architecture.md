# エージェントアーキテクチャ

AI エージェントシステムの責務分離の原則。ツール・フレームワーク非依存。

## 3層分離

エージェントの構成要素を以下の3層に分離する。

| 層 | 責務 | 例 |
|---|---|---|
| オーケストレーター | いつ・どの順で実行するか | タスク管理、DAG 解決、並列実行制御 |
| ワークフロー | 何をどうやるか | TDD 手順、調査手順、セルフチェック、エスカレーション |
| リファレンス | どう書くか・何を使うか | コーディング規約、テストガイドライン、技術選定 |

### 境界ルール

- オーケストレーターはワークフローの**中身を知らない**。タスクタイプで委譲するだけ
- ワークフローはオーケストレーターの**存在を前提としない**。単体でも実行可能であること
- リファレンスは**静的な知識**。判断ロジックやフロー制御を含まない
- ワークフローからリファレンスを参照してよい。逆は不可

### なぜ分離するか

- **オーケストレーター + ワークフロー混在**: 実行順序の変更がワークフロー定義に影響する。新しいワークフローの追加にオーケストレーターの変更が必要になる
- **ワークフロー + リファレンス混在**: コーディング規約の変更が全ワークフロー定義の更新を要求する。規約の共通化ができない
- **全部混在**: 1つの変更が全体に波及する。テスト不能

## サブエージェント設計の原則

### コンテキスト分離

親エージェントの設定・フック・指示がサブエージェントに漏洩してはならない。

- サブエージェントには必要な情報だけをプロンプトとして渡す
- 親の設定ファイルやフックが暗黙的に継承される仕組みは無効化する
- ワークフロー定義はプロンプトに直接注入する（サブエージェントが設定ファイルを読みに行かない）

### タスクタイプとワークフローの動的バインド

- タスクタイプは固定の列挙値ではなく、ワークフロー定義から動的に解決する
- ワークフローの追加・削除でタスクタイプが自動的に増減する
- オーケストレーターのコード変更なしに新しいワークフローを追加できる
