## フェーズ分割

大きなタスクは依存関係に基づいてフェーズに分割する。各フェーズが1回の実装・レビューサイクルを回す。

後続フェーズが前のフェーズの成果物に依存する場合、必ず別フェーズにする。
1サイクル内の依存順整理（先にAを実装してからBを実装）で済む場合はフェーズ分割不要。

```
例: アプリを1から作る
  Phase 1: モデル定義・共通インターフェース
  Phase 2: 基盤機能（認証、DB接続等）
  Phase 3: 各機能の実装（並列可）
```

単一フェーズで完結するタスクではフェーズ分割は不要。

## 実装・レビューサイクル（各フェーズ共通）

オーケストレーター（自分）が実装者とレビュアーを別エージェントとして立てる。
レビュアーは実装のコンテキストを持たない状態でレビューすることで、フレッシュな視点を確保する。
小規模タスク（単一ファイルの軽微な修正等）では自分で回してよい。

```
├── Step 0: 調査
│   技術選定や仕様確認が必要なら orchestrate-research で調査する
│
├── Step 1: 計画
│   変更対象ファイルと方針を整理する
│
├── Step 2: テスト作成 → テストレビュー
│   実装者がテストを書き、レビュアーが網羅性を確認する
│
├── Step 3: 実装 → 実装レビュー
│   実装者がテストを通す実装を行い、レビュアーが品質を確認する
│
└── Step 4: 修正・検証
    レビュー指摘を修正し、全テスト pass・ビルド確認する
```

### 調査（Step 0）

orchestrate-research スキルに従ってリソースにアクセスし、必要な情報を収集する。

- **要件の調査**: 何を作るか不明確な場合、ユーザーの意図や対象ドメインの仕様を調べる
- **設計の調査**: どう作るかについて、ベストプラクティス・既存コードのパターン・ライブラリの推奨用法を調べる

新規実装や設計判断を伴う変更では、設計の調査を必ず行う。
既存コードの軽微な修正（バグ修正、リネーム等）のみスキップしてよい。

### 計画（Step 1）

- 変更対象ファイルを列挙する
- ファイル間の依存関係を整理し、並列実行可能な単位に分割する
- 共有するインターフェース（型定義、API 契約等）を先に確定する
- 要件が不明確、または判断が分かれる設計上の選択肢がある場合は、実装に進まずユーザーに確認する。推測で実装しない

### テスト作成 → テストレビュー（Step 2）

**実装者**が計画で定義した振る舞いをテストとして先に書く。この時点ではテストは失敗する（Red）。

テストが不要なケース（設定ファイルの変更、既存テストが十分なリファクタリング、プロトタイプ等）はスキップしてよい。

**レビュアー**がテストをレビューする:

```
以下のテストをレビューせよ。
- テストファイル: [ファイルパス一覧]
- テスト対象の振る舞い: [何をテストしているか]
- 観点: 網羅性（正常系・異常系・境界値）、テストの妥当性、過不足
- 問題があれば具体的な修正案を示すこと
```

### 実装 → 実装レビュー（Step 3）

**実装者**がテストを通す実装を行う。実装者はテスト作成と同じエージェントでよい（コンテキストを共有するため）。

```
以下のファイルを変更せよ。
- 対象: [ファイルパス]
- 変更内容: [具体的な指示]
- 守るべきインターフェース: [型定義や API 契約]
- 対応するテスト: [テストファイルパス]
- 既存のコードスタイルに従うこと
```

並列実装時は、共有リソース（同一ファイルへの同時書き込み等）の競合を避ける。

**レビュアー**が実装をレビューする。実装者とは別のエージェントを使う:

```
以下の変更をレビューせよ。
- 変更ファイル: [ファイルパス一覧]
- 変更の意図: [何を実現するための変更か]
- 観点: 正確性、一貫性、エッジケース、セキュリティ
- 問題があれば具体的な修正案を示すこと
```

### 修正・検証（Step 4）

- レビュー指摘を分類する（必須修正 / 推奨 / 軽微）
- 必須修正がある場合は修正後に再レビュー（Step 3 を繰り返す）
- 推奨・軽微はまとめて対応する
- 原因不明のエラーが発生した場合は orchestrate-research で調査してから対処する
- 全テスト pass・ビルド確認で完了
- 検証が失敗した場合は原因を修正して再検証する
